# ARCHITECTURE.md — Общая Системная Архитектура Платформы

---

## 1. Обзор Системы и Назначение

Система представляет собой высокопроизводительную монолитную веб-платформу для проведения очных кейс-чемпионатов и хакатонов (нагрузка: 200–300 участников + жюри и администраторы).

### Главные инженерные приоритеты:

* **Высокая отказоустойчивость:** Работа без сбоев и просадок производительности в моменты пиковой нагрузки (дедлайн сдачи проектов).
* **Мгновенный отклик:** Использование скомпилированного Go-бинарника и асинхронных неблокирующих I/O операций.
* **Строгая безопасность:** Защита от состояния гонки (Race Conditions) при формировании команд, валидация прав доступа на базе ролей (RBAC), обработка сессий через `HttpOnly` / `Secure` Cookies.
* **Автономность:** Минимальное количество внешних инфраструктурных сервисов (отказ от Redis и микросервисной инфраструктуры).

## 2. Архитектурный Стек и Инфраструктура

```text
[ Client (Browser) ]
         │ (HTTPS / HttpOnly Cookie)
         ▼
[ Nginx (Reverse Proxy & SSL) ]
         │ (HTTP / Local Loopback)
         ▼
[ Golang Application Monolith ]
   ├── REST API v1 Router
   ├── Middleware Chain (Auth, Role, HardLock)
   ├── In-Memory Caching (sync.RWMutex)
   └── Services & Repositories
         │ (pgxpool / SQL)
         ▼
[ PostgreSQL 16+ Database ]

```

### Компоненты стека:

* **ОС Хоста:** Arch Linux.
* **Reverse Proxy:** Nginx (SSL termination, заголовок `X-Forwarded-For`, ограничение частоты запросов `limit_req`).
* **Внешний доступ:** Cloudflare Tunnel (`cloudflared`) для проброса трафика без необходимости выделения прямого публичного IP.
* **Backend Runtime:** Golang (компилируемый бинарник под `systemd`).
* **Database:** PostgreSQL 16+ (драйвер `pgx/v5` с connection pool).
* **Frontend:** Server-Driven UI / Static Assets (HTML5, Tailwind CSS, Vanilla JS / HTMX).

## 3. Топология Сети и Сетевое Взаимодействие

1. **Входной трафик:** Клиентский трафик проходит через CDN Cloudflare, оттуда по шифрованному туннелю `cloudflared` попадает на локальный Nginx хоста (`127.0.0.1:8080`).
2. **Проксирование:** Nginx выполняет функцию SSL-терминации, отдает статические файлы (CSS, JS, изображения) и проксирует API-запросы `/api/v1/*` на Go-приложение (`127.0.0.1:8000`).
3. **Безопасность соединений:** Прямой доступ к портам Go-приложения и БД PostgreSQL из внешней сети полностью заблокирован на уровне `iptables` / `nftables`.

## 4. Архитектурные Слои Приложения (Clean Architecture)

Внутри Go-монолита применяется четкое разделение ответственности по слоям:

```text
+-------------------------------------------------------+
|                Delivery Layer (HTTP)                  |
|  - Routers, Handlers, Middlewares (Auth, HardLock)    |
+-------------------------------------------------------+
                           │
                           ▼
+-------------------------------------------------------+
|                 Service Layer (Domain)                |
|  - Business Logic, State Machine, Validations         |
+-------------------------------------------------------+
                           │
                           ▼
+-------------------------------------------------------+
|               Repository Layer (Data)                 |
|  - PostgreSQL Access, Transactions, SQL Queries       |
+-------------------------------------------------------+

```

1. **Delivery Layer:** Принимает HTTP-запросы, распаковывает DTO, извлекает JWT из Cookie, передает управление в сервисный слой и форматирует JSON-ответы / HTTP-статусы.
2. **Service Layer:** Содержит изолированную бизнес-логику (проверка состава команд, логика Hard Lock, расчет суммарных оценок). Не знает о деталях HTTP или SQL.
3. **Repository Layer:** Отвечает за прямое взаимодействие с PostgreSQL через подготовленные SQL-запросы (`pgxpool`). Управляет ACID-транзакциями при параллельных мутациях.

## 5. Стратегия Безопасности и Авторизации

### 5.1. Stateless JWT в HttpOnly Cookie

* При успешной авторизации (`POST /api/v1/auth/login`) сервер генерирует signed JWT.
* Токен передается в заголовок `Set-Cookie` с параметрами: `HttpOnly=true`, `Secure=true`, `SameSite=Lax`, `Path=/`.
* Клиентский JavaScript **не имеет доступа** к токену, что нейтрализует угрозу XSS-атак.

### 5.2. Ролевая модель (RBAC)

Каждый токен содержит поле `role`:

* `USER` — Базовый доступ (профиль, управление своей командой, сдача решения капитаном).
* `JURY` — Изолированный доступ к реестру всех команд и выставлению собственных оценок.
* `ADMIN` — Доступ к сводной статистике и выгрузке `.xlsx` отчета.

### 5.3. Секретный ключ жюри

Регистрация аккаунта жюри выполняется на эндпоинте `/api/v1/jury/register` с обязательным указанием `JURY_REGISTRATION_KEY`. Сравнение ключа бэкендом происходит за константное время для предотвращения timing attacks.

## 6. Решение Задач Параллелизма и Гонки Данных (Concurrency Control)

Для предотвращения ситуации, когда в команду с лимитом в 4 человека одновременно вступают несколько участников:

1. **Транзакции PostgreSQL:** Любые действия по изменению состава команды (`Join`, `Kick`, `Leave`) выполняются в рамках транзакций.
2. **Пессимистическая блокировка:** Внутри транзакции выполняется запрос `SELECT ... FROM teams WHERE invite_code = $1 FOR UPDATE;`. Это блокирует строку команды на время выполнения транзакции, выстраивая конкурентные запросы в строгую очередь.

## 7. Мониторинг и Логирование

* **Healthcheck:** Эндпоинт `GET /api/v1/health` используется Nginx и локальными сервисами мониторинга для проверки Liveness/Readiness.
* **Логирование:** Вывод логов в `stdout` / `stderr` в структурированном JSON-формате (библиотека `slog` из стандартной библиотеки Go) для агрегации через `systemd-journald`.
