# business-logic.md — Спецификация Бизнес-Логики и Правил Системы

---

## 1. Системные Константы и Ограничения

Все бизнес-правила и ограничения зафиксированы на уровне констант и не подлежат динамическому изменению во время работы системы без перезапуска / обновления конфига:

```text
TEAM_MIN_MEMBERS       = 2        # Минимальный состав команды для сдачи работы
TEAM_MAX_MEMBERS       = 4        # Максимальная вместимость команды
INVITE_CODE_LENGTH     = 8        # Длина инвайт-кода (символы: A-Z, 0-9)
JWT_EXPIRATION_HOURS   = 24       # Время жизни JWT-токена в HttpOnly Cookie
HARD_LOCK_BEFORE_DEADLINE = 1h    # За 1 час до дедлайна блокируются мутации состава
SCORE_MIN_VALUE        = 0        # Минимальный балл по критерию
SCORE_MAX_VALUE        = 10       # Максимальный балл по критерию

```

## 2. Конечный Автомат Состояний Пользователя (User State Machine)

Каждый пользователь в системе находится строго в одном из 3-х базовых состояний:

```
    [ NO_TEAM ] 
      │    │
      │    └───> (Вход по invite_code) ───> [ IN_TEAM ]
      │                                       │
      └───────> (Создание команды) ───────────┴───> [ CAPTAIN ]

```

### Матрица Переходов и Допустимых Действий

| Действие | `NO_TEAM` | `IN_TEAM` | `CAPTAIN` |
| --- | --- | --- | --- |
| **Создать команду** | ✅ | ❌ | ❌ |
| **Войти по инвайт-коду** | ✅ | ❌ | ❌ |
| **Выйти из команды (`leave`)** | ❌ | ✅ | ❌ (Только после передачи прав) |
| **Исключить участника (`kick`)** | ❌ | ❌ | ✅ |
| **Передать права капитана (`transfer`)** | ❌ | ❌ | ✅ |
| **Расформировать команду (`disband`)** | ❌ | ❌ | ✅ |
| **Загрузить/обновить ссылку (`submit`)** | ❌ | ❌ | ✅ (При составе $\ge 2$ чел.) |
| **Перейти на `/no-team` (TG-чат)** | ✅ | ❌ | ❌ |

## 3. Правила Жизненного Цикла Команды

### 3.1. Создание команды

1. Пользователь со статусом `NO_TEAM` отправляет название команды (`team_name`).
2. Бэкенд генерирует случайный 8-значный криптографически стойкий `invite_code` (буквы в верхнем регистре и цифры).
3. Создатель команды автоматически получает роль `CAPTAIN` и привязывается к `team_id`.

### 3.2. Вступление в команду

1. Пользователь вводит 8-значный `invite_code`.
2. Бэкенд запрашивает команду с блокировкой строки (`FOR UPDATE`).
3. **Проверка 1:** Пользователь не должен состоять в другой команде.
4. **Проверка 2:** Текущее количество участников в команде $< 4$.
5. При успехе пользователь получает статус `IN_TEAM`. При $COUNT = 4$ роут возвращает ошибку `TEAM_FULL (400)`.

### 3.3. Мутации состава команды

* **Исключение (`kick`):** Капитан может исключить любого участника, кроме себя. Исключенный пользователь получает статус `NO_TEAM`.
* **Выход (`leave`):** Обычный участник с ролью `IN_TEAM` может покинуть команду в любой момент до наступления Hard Lock. Капитан **не может** просто вызовать `leave` — он обязан предварительно передать права капитана или расформировать команду.
* **Передача прав (`transfer-ownership`):** Капитан назначает нового капитана из текущего состава команды. Сам бывший капитан становится обычным участником (`IN_TEAM`).
* **Расформирование (`disband`):** Капитан полностью удаляет команду. Все участники команды (включая капитана) атомарно переводятся в статус `NO_TEAM`. Сданная ссылка на решение удаляется.

## 4. Сдача Решений и Временные Замки (Hard Lock)

### 4.1. Валидация сдачи решения (`POST /team/submit`)

Сдача решения разрешена строго при выполнении всех 3-х условий:

1. Запрос отправлен пользователем с ролью `CAPTAIN`.
2. В составе команды состоит **от 2 до 4 человек**.
3. Формат отправленной строки соответствует шаблону валидного URL (`http://` или `https://`).

### 4.2. Блокировка за 1 час до дедлайна (Team Hard Lock)

За 1 час до времени наступления `submission_deadline` система автоматически блокирует любые изменения в составе команд:

* Блокируются роуты: `kick`, `leave`, `disband`, `transfer-ownership`.
* При попытке вызова возвращается `403 Forbidden` (`"Team mutations are locked 1 hour before submission deadline"`).
* **Исключение:** Сдача и перезапись ссылки на решение капитаном **продолжает работать**.

### 4.3. Дедлайн сдачи (Submission Hard Lock)

Ровно в момент времени `submission_deadline` (00:00:00 UTC):

* Бэкенд мгновенно блокирует роут `POST /team/submit`.
* Кабые-либо изменения или загрузка новых ссылок становятся недоступны.

## 5. Оценивание и Независимые Сессии Жюри

### 5.1. Изоляция сессий

1. Жюри аутентифицируется через изолированную систему аккаунтов.
2. Вся работа эксперта происходит в контексте его персонального `jury_id`.
3. Оценки хранятся в БД как независимые записи `(jury_id, team_id, criterion_id, score)`.
4. Жюри не могут просматривать оценки, выставленные другими членами жюри, и не видят итоговую суммарную таблицу.

### 5.2. Шкала и Критерии Оценивания

* Каждая работа оценивается по фиксированному набору критериев ($1..N$).
* Оценка по каждому критерию — целое число от `0` до `10`.
* Перезапись оценок конкретным жюри доступна до момента закрытия этапа проверки администратором.

## 6. Административный Вывод и Формула Подсчета

Платформа является инструментом учета и агрегации баллов и не выносит автоматических решений о победителях.

### Формула Итогового Балла Команды:

Ниже приведен читаемый текстовый вариант формулы подсчета баллов и оформленный блок с критериями оценивания для `business-logic.md`.

---

### Формула Подсчета Баллов (Читаемый формат)

**Итоговый балл команды = Сумма всех оценок от всех членов жюри по всем критериям**

$$\text{Итоговый балл команды} = \text{Сумма}(\text{Оценки жюри})$$

#### Детализация алгоритма расчета:

1. Для каждого эксперта жюри суммируются баллы, выставленные им по всем 6 критериям (от 0 до 10 за каждый критерий).
2. Баллы всех членов жюри, оценивших данную команду, складываются в единую итоговую сумму.
3. В случае, если один из экспертов не оценил команду, его отсутствие не блокирует расчет — итоговый балл формируется из фактически выставленных оценок.
