# Frontend visual acceptance

> **Purpose:** current human evaluation of the React frontend, separate from
> the stable design constitution (`design-direction.md`) and product UX model
> (`experience-model.md`). This file is intentionally transient and is written
> only after human review.
>
> A technically valid implementation is not automatically visually accepted.

## Current status

**Stage 4H human review completed 2026-08-12 — verdict: ACCEPT — PUBLIC VISUAL FOUNDATION**

Stage 4H (`ce79c32`) is accepted as the public visual baseline. The dark
content-first direction, restrained pseudo-3D/material language, stronger hero
chassis, connected Format progression and wider information-led Schedule/FAQ
composition now form a coherent foundation. The public frontend is intentionally
minimal, spatial and restrained rather than illustration-heavy or SaaS-card
driven.

The next approved work is **Phase 5A — Participant Workspace Foundation**. The
public site is not the active design problem.

## Accepted public foundation

Keep:

- near-black/deep-navy canvas with warm light text;
- one restrained deep-red accent;
- hero as the primary Z2 spatial identity moment;
- hero composition based on one integrated chassis/assembly rather than a
  collection of decorative cards;
- Format as one connected shallow progression;
- Schedule deriving visual weight from date/time/data hierarchy;
- FAQ as a wide but flat typographic surface;
- absence of decorative illustration scenes;
- restrained Motion budget;
- mobile/reduced-motion flattening;
- no Three.js/WebGL/new visual runtime.

Do not reopen the old Stage 4E illustration/poster direction.

## Why Phase 5A is next

Human review of the current authenticated area found a concrete product/layout
defect: page-level participant content can render at the viewport's top-left
edge instead of inside a coherent workspace. This is treated as an
**authenticated layout contract problem**, not a typography or margin bug.

The participant area also remains a placeholder rather than a designed product
workspace. The next UX/UI value comes from implementing real participant
state, navigation and next-action hierarchy — not from adding more public
decoration.

## Phase 5A UX/UI acceptance questions

1. Does every authenticated USER route participate in one stable workspace
   shell/content-bound contract?
2. Is the viewport-corner defect fixed architecturally rather than with
   route-local offsets?
3. Does `/dashboard` immediately communicate participant/team state and the
   next meaningful action?
4. Is the no-team state deliberate, truthful and actionable?
5. Does a has-team state feel like a competition workspace rather than a generic
   dashboard?
6. Are cards/widgets used only when content is genuinely self-contained?
7. Is product navigation task-oriented and compact rather than a generic icon
   sidebar?
8. Does shallow spatial depth communicate hierarchy/state rather than decorate
   routine product content?
9. Does desktop use the available workspace confidently without stretching body
   copy?
10. Does mobile recompose into a clear task flow with no hidden critical state?
11. Are backend lifecycle/lock/deadline semantics represented truthfully?
12. Did accepted public Stage 4H surfaces remain visually stable?

## Documentation ownership

Coding agents do not declare visual/UX acceptance and do not edit this file.
Human review + ChatGPT Web own this document unless the user explicitly changes
that policy.

## Gate

Phase 5A implementation may proceed. Phase 5B must not begin until Phase 5A has
received explicit human UX/UI acceptance here. A technically valid commit is not
enough.
